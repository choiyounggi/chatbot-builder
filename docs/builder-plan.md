**가정** (틀리면 말해 주세요)
- A1. "동작 방법과 원리가 유사하게"는 **기능과 동작 규칙**을 카카오 오픈빌더에 맞춘다는 뜻이다. 화면 디자인·로고·문구는 베끼지 않고 우리 디자인으로 만든다.
- A2. 카카오톡 채널 연결(운영/개발 채널), 비즈월렛, 그룹 챗봇, 성별·연령 인사이트는 카카오 플랫폼에만 있는 기능이라 이번 범위에서 뺀다(§7). 단, 엔진을 나중에 카카오 스킬 서버로 붙일 수 있게 응답 형식은 카카오와 호환되게 고른다.
- A3. 엔진의 대화 원리(시나리오 스택, 이벤트 기록, 임베딩 + 분류기)는 그대로 두고, 빌더가 그 위에 카카오식 "블록" 화면을 씌운다.

## 1. 카카오 i 오픈빌더 기능 전체 정리와 우리 상태

조사 방법:
- 영기 계정으로 로그인된 브라우저에서 테스트용 봇 하나를 **읽기 전용**으로 열어 메뉴와 편집 화면을 하나씩 봤다(2026-11-10). 저장·생성·배포는 하지 않았고, 작업이력으로 변경 없음을 확인했다. 표에서는 [화면 확인]으로 표시한다.

## 2. 동작 원리를 카카오와 맞추는 방법

엔진의 구조는 유지하고, 빌더가 카카오식 개념을 엔진 개념으로 바꿔 저장한다.

### 2.1 블록 = 의도 + 시나리오
- 빌더에서 블록을 만들면, 같은 ID의 의도(예문)와 시나리오(그 의도로 시작)를 함께 만든다.
- 블록 화면의 칸이 시나리오 단계로 바뀌는 순서: **파라미터(필수) → `collect` 단계**, **스킬 → `action` 단계**, **응답 말풍선 1~3개 → `respond` 단계들**. 카카오 블록과 같은 순서로 실행된다.
- 엔진의 고급 단계(`call` 다른 블록 호출, `branch` 조건 분기)는 블록 화면의 "고급" 칸으로 둔다. 카카오에는 없지만 날씨 시나리오처럼 이미 쓰고 있다.
- 블록 이름은 `label`이다. ID는 바뀌지 않아서 이름을 바꿔도 진행 중인 대화가 깨지지 않는다(엔진 Phase 6에서 검증됨).
- 블록 종류 세 가지. 엔진 규칙 "의도 하나는 시나리오 하나만 시작"(엔진 `loader.py`의 트리거 중복 검사) 덕분에 트리거 블록은 항상 1:1이다.

  | 종류 | 엔진에서 | 예 |
  |---|---|---|
  | 트리거 블록 | 의도(예문 1개 이상) + 그 의도로 시작하는 시나리오 | 날씨 묻기 |
  | 호출 전용 블록 | 트리거 없는 시나리오(다른 블록의 `call`·`branch`·바로연결로만 시작) | 날씨 조회 실패 안내 |
  | 시스템 블록 | 예문 없는 고정 시나리오: 웰컴·폴백·탈출 | 폴백 |

- 기존 봇을 불러올 때 시나리오에 연결되지 않은 의도(예: `out_of_scope`)는 "블록 없는 발화"로 따로 보여 준다. `out_of_scope` 예문은 폴백 블록 화면의 "모르는 질문 예시"로 편집한다.

### 2.2 발화 매칭
- 엔진은 이미 "정확히 일치하면 바로 매칭, 아니면 임베딩 분류기"로 동작한다. 카카오의 패턴 발화 + 머신러닝 발화와 같은 2단 구조다.
- 다른 점: 카카오는 패턴 발화의 어순이 같으면 조사·어미가 달라도 매칭한다 [공식 문서]. 엔진은 띄어쓰기·문장부호만 무시한다.
- **추가 (핵심어 일치):** Kiwi로 형태소를 나눈 뒤 조사(J*), 어미(E*), 접사(XS*·XP*), 문장부호(S* 중 SL·SN 제외)를 빼고 남은 형태소의 순서열이 예문과 같으면 정확 매칭으로 본다. 용언은 어간만 비교하므로 "알려줘"와 "알려주세요"가 같아진다.
  - 켜는 조건: 샘플 봇 교차검증에서 새 오답 0개, 대화 32개 결과 변화 없음.
  - Kiwi는 엔티티 추출과 락을 공유하지 않도록 별도 인스턴스를 쓴다.

### 2.3 파라미터와 되묻기
- 필수 파라미터: 지금의 `collect`와 같다(없으면 되묻고, `max_attempts`를 넘으면 포기 안내).
- 선택 파라미터: 발화에 있으면 슬롯에 넣고, 없으면 묻지 않는다. **엔진 추가.**
- 기본값: 값이 없을 때 넣는 값. **엔진 추가.**
- 검증: 지정한 스킬을 불러 값이 맞는지 확인하고, 아니면 실패 메시지와 함께 다시 묻는다. **엔진 추가.**

### 2.4 응답
- 카카오 응답 형식(텍스트, 이미지, 기본 카드, 리스트 카드, 케로셀, 바로연결)을 엔진 응답 스키마에 추가한다. 이름과 필드는 카카오 스킬 응답 형식과 1:1로 맞춘다. 나중에 엔진을 카카오 채널에 붙일 때 그대로 변환하기 위해서다.
- 카카오의 제한(말풍선 3개, 바로연결 10개·14자, 케로셀 10장)은 **경고**로만 띄운다. 엔진 자체는 채널을 가리지 않는다.

### 2.5 대화 흐름 규칙
| 카카오 | 엔진 |
|---|---|
| 웰컴 블록 | 새 세션의 첫 요청이 "시작 이벤트"면 웰컴 시나리오 실행 (**추가**) |
| 폴백 블록 | 지식베이스(§3) → 그래도 없으면 폴백 시나리오 |
| 탈출 블록 | 탈출 의도 → 진행 중인 시나리오 전부 취소 |
| 되묻기 최대 횟수 | `max_attempts` (있음) |
| 최대 시간 | 마지막 턴 후 N분이 지나면 다음 발화에서 처음부터 + 안내 (**추가**) |

### 2.6 테스트 → 저장 → 배포
- 카카오: 블록을 저장하면 봇테스트와 개발 채널에서 바로 확인하고, 배포해야 운영 채널에 반영된다 [화면 확인: "블록 저장 후 테스트할 발화를 입력해주세요"].
- 우리는 학습을 두 종류로 나눈다.

  | | 테스트 빌드 | 배포 학습 |
  |---|---|---|
  | 언제 | 초안 저장마다 자동(연속 저장은 마지막 것만) | "배포" 버튼 |
  | 하는 일 | 분류기 적합만(교차검증 없음) | 교차검증 평가 + macro-F1 0.90 기준 + 적합 |
  | 예문 조건 | 의도 2개 이상, 의도마다 1개 이상 | 의도마다 5개 이상(교차검증 5겹) |
  | 결과 | 임시 파일, 버전 목록에 안 남음, 30분 뒤 삭제 | 버전 번호(v1, v2…)가 붙고 배포 히스토리에 남음 |
  | 대화 | 봇테스트 패널만 | 사용자 대화 |

  - 이렇게 하면 예문이 적은 새 블록도 바로 테스트할 수 있다. 기준 미달·예문 부족은 배포 단계에서만 막고, 이유(의도별 F1, 부족한 의도)를 보여 준다.
  - 테스트 빌드는 운영 버전 캐시와 **별도 캐시**(최대 2개, 30분)에 올린다. 운영 세션이 고정된 버전을 밀어내지 않는다. 테스트 빌드가 만료되면 테스트 대화는 운영 버전으로 넘어가지 않고 "다시 저장해 주세요"(410)로 끝난다.
  - 학습과 대화가 임베딩 워커 하나를 함께 쓰는 문제(엔진 `serving.py`의 큐 하나): 큐를 **두 단계 우선순위**로 바꿔 대화 요청을 항상 먼저 처리하고, 학습 문장은 작은 묶음(예: 32개)으로 넣는다. 학습은 조금 느려지고 대화 지연은 지킨다.

## 3. 지식베이스(RAG) 설계 — 검색형 (D1 추천안)

### 3.1 동작
1. 관리자가 지식베이스에 **FAQ(질문 + 답)** 또는 **문서**(텍스트·마크다운·PDF)를 올린다.
2. 엔진이 색인을 만든다. 모델은 NLU와 같은 `dragonkue/snowflake-arctic-embed-l-v2.0-ko`다.
   - **FAQ 질문**: NLU 예문처럼 `query: ` 접두어로 인코딩한다. 사용자 질문과 FAQ 질문을 같은 방식으로 비교하므로, 점수를 NLU의 "가장 가까운 예문 유사도"와 같은 잣대로 볼 수 있다.
   - **문서 조각**: 문단 단위(약 300~500자, 겹침 약 50자)로 나누고 접두어 없이 인코딩한다(모델 카드 사용법 [확인]). 엔진 임베더는 지금 모든 문장에 같은 접두어를 붙이므로 "문서용 인코딩"을 추가한다(E11).
   - 사용자 발화는 NLU가 이미 `query: `로 인코딩한 벡터를 **그대로 재사용**한다. 임베딩을 두 번 하지 않는다.
3. **순위**: 임베딩 검색과 형태소 BM25 결과를 RRF로 합친다. RRF는 순위만 정한다.
4. **답할지 판단**: 1위 후보의 코사인 점수로만 정한다. RRF 점수는 질문이 지식베이스와 무관해도 비슷한 값이 나와서 판단에 쓸 수 없다. 기준은 FAQ용(질문-질문)과 문서용(질문-조각)을 따로 둔다. 둘 다 평가셋의 개발용 절반에서 정하고 나머지 절반으로 확인한다.
   - **즉문즉답형**: 1위 FAQ의 답 또는 문서 조각을 출처(문서 이름)와 함께 보여 준다.
   - **답안 추천형**: 기준을 넘은 상위 3개를 버튼으로 보여 주고, 사용자가 고르면 그 답을 보여 준다.
5. 기준 미만이면 폴백 블록으로 간다. 그 발화는 학습대기 목록에 "지식베이스에도 없음"으로 남는다(이벤트에 지식베이스 검색 결과를 기록하는 필드 추가).

**대화 규칙 안에서의 위치** (엔진 `interpreter.py` 규칙 순서 기준)

| 상황 | 동작 |
|---|---|
| 블록 의도가 확실함(규칙 3) | 블록. 단, FAQ 질문 유사도가 블록의 가장 가까운 예문 유사도보다 0.05 이상 높으면 지식베이스 (같은 잣대로 비교 가능한 FAQ에만 적용) |
| 두 블록 사이에서 애매함(규칙 5, 되묻기) | 지식베이스 1위가 기준 이상이면 지식베이스, 아니면 지금처럼 되묻기 |
| 폴백(규칙 6) | 지식베이스 → 기준 미만이면 폴백 |
| 시나리오가 값을 기다리는 중 | 바뀌지 않는다: 지금처럼 되묻는다. 단 지식베이스 1위가 높은 기준(전환 기준과 같은 0.80 수준, 평가로 확정) 이상이면 답한 뒤 같은 질문을 다시 묻는다 |

시나리오 안에서도 쓸 수 있게 `knowledge` 단계를 추가한다. 예: "환불 규정 질문이면 지식베이스에서 찾아 답하기".

### 3.2 저장과 버전
- 카카오처럼 지식베이스는 **봇과 별도로 만들고 버전으로 관리**한다.
- "어느 지식베이스의 어느 버전"은 봇 문서가 아니라 **배포 기록**에 넣는다. 배포 = (봇 버전, 지식베이스 버전) 한 쌍이다.
  - 봇 문서가 그대로라 지식베이스만 바꿔도 봇을 다시 학습하지 않는다(봇 버전 = 문서 해시이기 때문).
  - 세션은 시작할 때의 (봇 버전, 지식베이스 버전) 쌍에 고정된다. `SessionStarted` 이벤트에 지식베이스 버전을 추가한다. 대화 도중 답의 근거가 바뀌지 않는다.
  - 되돌리기는 쌍 단위다. 봇을 되돌리면 그때의 지식베이스도 함께 돌아간다.
- 벡터 저장: 지금 쓰는 Postgres에 pgvector 확장이 이미 들어 있다(`docker-compose.yml`의 `pgvector/pgvector:pg17` [확인]). DB 없이 돌릴 때는 메모리 저장(numpy)으로 대신한다. 엔진 저장소의 메모리/Postgres 두 구현 원칙과 같다.

### 3.3 평가 (엔진 Phase 0와 같은 방식)
- 샘플 지식베이스와 평가 질문셋을 만든다. 질문은 합성해서 만든다(실제 로그 문장을 쓰지 않는다).
  - 답이 있는 질문 150개 이상, 답이 없는 질문 50개 이상(폴백이어야 함), 블록이 받아야 할 질문 50개 이상.
- 측정 (모든 값에 부트스트랩 95% 구간을 같이 적는다, 엔진 Phase 0과 같은 방식):
  - 검색 정답률: Recall@3, MRR
  - 답 없는 질문의 폴백 비율
  - **양방향 가로채기**: 지식베이스가 블록 질문을 가져간 비율, 블록이 지식베이스 질문을 가져간 비율
  - 지연 p95 (조각 1만 개 기준)
- 기준(제안): Recall@3 ≥ 0.90, 답 없는 질문의 폴백 ≥ 0.90, 가로채기 각각 ≤ 0.05, 지식베이스를 거치는 턴의 p95 ≤ 100ms. 점추정이 기준을 넘고 구간을 리포트에 적으면 통과로 본다. 임계값은 개발용 절반에서 정하고 나머지 절반으로 확인한다.
- 비교군: 임베딩만 / BM25만 / 하이브리드 / 하이브리드 + 재순위 모델(크로스 인코더, 생성 안 함). 가장 단순한 통과안을 고른다.

### 3.4 생성형으로 확장할 자리 (지금은 만들지 않음)
- 검색 결과(상위 조각 + 출처)를 받는 "답 작성기" 인터페이스만 정해 둔다. 기본 구현은 "1위 답을 그대로 반환"이다.
- 나중에 로컬 LLM 구현을 꽂으려면 영기 결정이 필요하다. 지연(수 초)과 근거 없는 답을 막는 규칙을 그때 따로 계획한다.

## 4. 빌더 앱 설계 (이 레포)

### 4.1 화면 (카카오 메뉴 구조를 따른다)
- **봇 목록**: 만들기, 검색, 상태(초안만 있음 / 배포됨 / 학습 중).
- **시나리오**:
  - 왼쪽: 시나리오(폴더) → 블록 트리. 기본 시나리오에는 웰컴·폴백·탈출이 있고, 검색이 된다.
  - 가운데: 블록 편집기(이름, 사용자 발화, 파라미터, 스킬, 응답 1~3개, 바로연결, 고급 단계).
- **엔티티 패널**(어디서나 열림): 나의 엔티티 편집, 시스템 엔티티 목록과 예시.
- **봇테스트 패널**(어디서나 열림): 학습된 초안 버전과 대화한다. 매 턴의 블록, 매칭 방식(정확/분류기/지식베이스), 신뢰도, 가장 가까운 예문, 파라미터, 스킬 호출 결과를 펼쳐 볼 수 있다.
- **스킬**: 목록, 만들기(URL·헤더·타임아웃·테스트 URL), 테스트 실행, 오류 내역.
- **학습**: 학습대기(빈도순, 기간·필터, 블록에 추가/무시), 학습이력.
- **분석**: 블록 호출 수, 블록 순위, 사용자(활성·신규·재방문), 세션, 지식베이스 응답률.
- **배포**: 배포 메모, 버전 번호, 배포 히스토리, 되돌리기.
- **작업이력**: 누가·언제·무엇을 바꿨는지.
- **머신러닝**: 유사도 5단계, 블록별 "정확 일치만", 의도 간 헷갈림 경고(예문 임베딩 유사도가 높은 쌍).
- **지식베이스**: FAQ·문서 관리, 조각 미리보기, 검색 테스트, 버전·배포.
- **설정**: 봇 이름, 응답 방식, 시나리오 설정(되묻기·최대 시간), 봇 삭제.

### 4.2 기술
- React + Vite + TypeScript (D2).
- 서버 상태(봇 초안, 버전, 학습 작업): TanStack Query.
- API 타입: 엔진 OpenAPI 스키마에서 생성한다(openapi-typescript). 엔진 API가 바뀌면 타입 검사에서 바로 깨진다.
- 표·차트·폼: 우리 컴포넌트로 직접 만든다. 디자인은 카카오와 다르게 우리 것으로 정한다.
- 테스트:
  - Vitest + Testing Library: 컴포넌트·변환 로직("블록 ↔ 의도+시나리오" 변환은 양방향 테스트).
  - Playwright: 실제 엔진을 띄우고 "블록 만들기 → 저장 → 학습 → 테스트 대화 → 배포 → 되돌리기"를 끝까지 돌린다.
- 로컬 실행: `npm run dev`. Vite 프록시가 엔진(`127.0.0.1:8000`)으로 넘긴다. 엔진은 `make serve`로 띄운다.

### 4.3 동시 편집
- 초안에 버전 번호(ETag)를 붙인다. 저장할 때 `If-Match`로 보내고, 다르면 412를 돌려준다. 화면은 "다른 곳에서 바뀌었어요"를 보여 주고 다시 불러온다.
- 조사한 빌더 6개 모두 실시간 공동 편집 충돌을 해결한다는 문서가 없었다 [조사]. "조용히 덮어쓰지 않기"까지를 목표로 한다.

### 4.4 유사도 5단계
- 카카오의 "유사도 낮음 ~ 매우 높음"을 고정 숫자로 두지 않는다. 임계값의 적정값은 봇과 예문마다 달라서 한 묶음으로 일반화되지 않는다.
- 대신 단계 = **"모르는 질문(out_of_scope)을 얼마나 거절할지" 목표**로 정의한다. 배포 학습 때 그 봇의 교차검증 예측에서 목표를 만족하는 가장 낮은 `similarity_threshold`·`intent_threshold`를 계산해 저장한다.

  | 단계 | 모르는 질문 거절률 목표 |
  |---|---|
  | 낮음 | 0.80 |
  | 보통 | 0.90 |
  | 다소 높음 | 0.95 |
  | 높음 | 0.97 |
  | 매우 높음 | 0.99 |

  - 목표 수치는 제안이다. 샘플 봇의 지금 기본값(0.30 / 0.39)은 거절률 0.97을 냈다(엔진 계획 Phase 3 결과).
  - 봇에 `out_of_scope` 예문이 없으면 계산할 수 없으므로 지금 기본값을 쓰고 화면에 알린다.
  - 테스트: 단계를 올릴 때 거절률이 줄지 않고, 블록 의도 재현율이 늘지 않음을 샘플 봇에서 확인한다.

### 진행 기록

**E-A (엔진, 2026-11-10) — 완료 조건 4개 통과**
- ① 학습 중 대화 지연: 배포 학습이 도는 동안 동시 4세션 p95 **46.6ms** ✅ (학습 없을 때 34.5ms, E-A 전 방식 760.6ms). 같은 설정으로 세 번 재서 46.0 / 45.9 / 46.6ms. 엔진 `docs/benchmarks/train_latency.md`.
  - 처음 설계("대화를 항상 먼저")는 대화가 쉬지 않으면 학습이 끝나지 않았다(실측 10분 넘게 멈춤). **둘 다 기다리면 번갈아 처리**로 바꿨다.
  - 학습 묶음 크기 실측: 8 → p95 55~58ms ❌, **4 → 46ms ✅ (학습 26초)**, 2 → 41ms (학습 47초). 4를 기본값으로 했다. 학습 시간은 4세션이 쉬지 않는 최악 부하 기준이다.
  - 학습 스레드 수 제한은 효과가 없었다(8 + 2스레드 58ms).
- ② 두 탭 동시 저장: 같은 리비전으로 저장하면 두 번째가 412 ✅ (메모리·Postgres 저장소 모두 테스트).
- ③ 테스트 빌드가 운영 세션의 고정 버전을 밀어내지 않음 ✅ (테스트).
- ④ 만료되거나 모르는 테스트 빌드 대화는 410, 운영 봇으로 넘어가지 않음 ✅ (테스트).
- 추가로 정한 것:
  - 테스트 빌드는 배포 학습보다 먼저 처리한다(작업 큐 우선순위).
  - 빌드마다 고유 폴더를 쓰고, 서버 시작 시 이전 실행의 테스트 빌드 파일을 지운다.
  - 테스트 대화 세션은 `<봇>~<세션>`이라 학습대기·통계에 섞이지 않는다.
  - 학습 작업은 메모리에만 있다. 서버가 다시 시작되면 잊히고, 빌더가 다시 요청한다.
  - 진행 상황은 `GET /jobs/{id}`(폴링)와 `GET /jobs/{id}/events`(SSE)로 본다.
- 알려진 한계:
  - 테스트 대화도 운영과 같은 저장소와 액션을 쓴다. 날씨 액션은 실제 날씨 API를 부른다(읽기만 함).
  - 테스트 세션 기록은 저장소에 남는다.

**B1 (빌더, 2026-11-10) — 뼈대**
- React 19 + Vite 8 + TypeScript 6(typescript-eslint가 아직 7을 지원하지 않음) + React Router + TanStack Query.
- 화면: 봇 목록(배포 상태: 배포됨·vN / 배포 안 된 변경 / 초안만), 봇 화면 셸(메뉴 8개 + 엔티티·봇테스트 패널), 설정(봇 이름 저장, ETag로 동시 편집 보호, 412 시 다시 불러오기 안내), 관리자 토큰 입력(탭을 닫으면 잊음), 엔진 미연결·저장소 장애 안내, 라이트/다크/시스템 테마. 아직 없는 메뉴는 어느 단계에서 만드는지 그대로 보여 준다.
- 디자인: Cobalt 계열(차가운 흰 바탕, 코발트 포인트 1색, 가는 선, 6px 모서리). 한글 UI라 Pretendard + JetBrains Mono로 바꿨다. 카카오 화면을 따라 하지 않았다.
- 엔진 쪽: 봇 목록 API `GET /v1/builder/bots`를 추가했다(엔진 PR).
- **계획과 다르게 한 것:** API 타입을 OpenAPI에서 생성하지 않고 직접 썼다. 엔진 응답 대부분이 `Any`로 선언돼 생성 타입이 비어 있기 때문이다. 엔진에 응답 모델을 붙인 뒤 생성으로 바꾼다(B2 전에).
- 검증: 테스트 35개(커버리지 문장 97.6%·분기 94.6%), 실제 엔진 + 브라우저로 토큰 입력 → 목록 → 이름 저장(리비전 증가, "배포 안 된 변경" 표시) → 되돌리기, 320/375/414/768px에서 가로 스크롤 없음.
- 리뷰 후 고친 것: 다시 불러오기가 실패해도 입력 중인 폼을 유지, 폼 안에 폼이 중첩되던 토큰 입력, 틀린 토큰 안내, 헤더에 못 넣는 문자가 든 토큰 거부, 422/428/400 안내(의미 없는 재시도 버튼 제거), 저장·패널 닫기 후 키보드 포커스 유지, 스크린 리더용 상태 영역, 좁은 화면에서 패널을 덮개(drawer)로, 앱 전체 오류 경계, 본문 바로가기, 터치 기기 44px 컨트롤.
- E2E(Playwright)는 B2에서 엔진을 테스트용 임베더로 띄울 수 있게 한 뒤 CI에 넣는다(실제 모델은 CI에서 너무 무겁다).
